# Онлайн-запись для студии маникюра: план реализации

> **Для исполнителей:** план выполняется по схеме из `.claude/CLAUDE.md`: Codex пишет код через `delegate-codex.sh`, Claude проверяет результат и коммитит. Порядок задач ведётся через superpowers:executing-plans. Шаги отмечаются чекбоксами (`- [ ]`).

**Цель:** работающее демо записи в вымышленную студию: сайт, панель менеджера, Telegram-бот для клиентов и двух мастеров, с проверкой настоящими действиями.

**Архитектура:** одно приложение Next.js содержит сайт, панель, webhook бота и ежедневную задачу. Правила записи живут в одном серверном модуле, сайт, бот и панель только вызывают его. Двойную запись запрещает ограничение PostgreSQL.

**Стек:** Node 24, Next.js 16, React 19, TypeScript, Tailwind 4, PostgreSQL, Drizzle, `pg`, grammY, `@date-fns/tz`, `jose`, Vitest, Playwright, `embedded-postgres`.

**Проект системы:** `docs/specs/2026-11-06-booking-design.md`.

**Статус:** одобрен заказчиком 2026-11-06, все три рекомендации приняты и внесены в проект системы.

## Global Constraints

- Часы по умолчанию: Пн–Пт 10:00–22:00, Сб 10:00–15:00, Вс выходной. Часовой пояс Europe/Moscow, в коде.
- Правила по умолчанию, меняются в панели: шаг слотов 30 минут, запись от 60 минут до 30 дней вперёд, самостоятельные изменения не позже чем за 120 минут, 3 переноса на запись. Пауза между клиентами по умолчанию 15 минут, задаётся у услуги.
- В коде: одна услуга за визит, шаг 5 минут для менеджера.
- Поля записи: только имя и телефон.
- Менеджер не может обойти запрет двойной записи. Лимит переносов и срок изменений его не ограничивают.
- Ошибка Telegram никогда не отменяет и не откатывает запись и всегда видна в журнале.
- Все действия менеджера проверяют сессию на сервере, включая каждое серверное действие.
- Чужую запись нельзя получить без её личной ссылки или привязанного чата.
- Секреты только в переменных окружения сервера. Codex не читает `.env`. Токен бота не попадает в браузер.
- База доступна только с сервера. В тестах и в работе один драйвер `pg`.
- Демо-записи никогда не называются реальными клиентами. На сайте нет отзывов, счётчиков клиентов и «нам доверяют». В панели постоянно видна пометка «Демо-данные».
- Интерфейс на русском. Запрещённые приёмы дизайна: тёмный slate с градиентными карточками, эмодзи-иконки, крем с терракотой, антиква с одним курсивным словом, моно-надписи прописными, тонкие линии-разделители, «→» в кнопках, бегущая строка. Главное на витрине: крупное фото предмета.
- Тесты базы идут на настоящем PostgreSQL через `embedded-postgres`. Проверено на этой машине 2026-11-06: PostgreSQL 18.6, `btree_gist` работает, путь с кириллицей и пробелом работает, из 20 параллельных вставок 1 успешна и 19 отклонены с кодом `23P01`. Docker на машине нет.
- Git: локальный репозиторий в `manicure-booking`, ветка `build/v1`. Без отдельной просьбы ничего не отправляется наружу.

## Review Focus

1. **Сброс демо во время работы посетителя** (старая личная ссылка, форма с исчезнувшими услугами, кнопка бота): понятное сообщение вместо ошибки 500. Тесты в T6, T8, T9.
2. **Устаревший выбор** (вкладка открыта давно, время прошло или стало слишком близко, старая кнопка бота): понятный отказ и новые варианты. Тесты в T3, T6.
3. **Другой часовой пояс** (сервер в UTC, посетитель во Владивостоке): всегда московское время. Тесты в T2, T8.
4. **Телефон в разном написании:** один клиент, мусор отклоняется понятной ошибкой. Тест в T3.
5. **Имя со спецсимволами, HTML, эмодзи и длиной 200 символов:** ограничение 60, текст экранируется в панели и не ломает сообщение Telegram. Тесты в T3, T4, T11.

export const STUDIO_TZ = 'Europe/Moscow';
export function computeDaySlots(input: {
  date: string;                                     // 'YYYY-MM-DD' в поясе студии
  hours: { opens: string; closes: string } | null;  // null: выходной
  durationMin: number; bufferMin: number;

## Этап 7. Проверка

### Task 14. Проверка как тестировщик

Исполнитель: Claude, без опоры на отчёты Codex.

**Файлы:** `docs/qa/report.md`.

Проект запускается в режиме `next build` и `next start` с постоянной локальной базой. Действия выполняются через интерфейс в браузере, результат сверяется запросами к базе.

| Сценарий заказчика | Как проверяем |
|---|---|
| Клиент видит свободное время и создаёт запись | Браузер, строка в `bookings` |
| Занятое время исчезает | Новая загрузка слотов, сверка с базой |
| Два одновременных запроса на один слот | Параллельные запросы через настоящий сервер, в базе одна запись |
| Перенос | Браузер, база, старое время снова доступно, новое занято |
| Отмена | Браузер, база, время снова доступно |
| Менеджер меняет расписание или закрывает время | Панель, затем попытка клиента через интерфейс и прямым запросом |
| Уведомления при создании, переносе и отмене | Журнал и заглушка Telegram, живой бот при наличии токена |
| Посторонний и чужая запись | Выдуманный токен, повтор запроса без cookie, чужая кнопка бота |
| Ошибка отправки | Заглушка возвращает ошибку: запись в базе есть, в журнале `failed`, в «Позвонить» есть строка |
| Телефон | Ширина 390 px, полный путь клиента и менеджера |
| Перезапуск | Остановить сервер и базу, запустить снова, сверить записи и галочки |

- [ ] **Шаг 1.** Прочитать код и требования, запустить `npm test`, `npm run test:e2e`, `npm run build`.
- [ ] **Шаг 2.** Пройти все сценарии. Для каждого записать: что сделал, что ожидалось, что получилось.
- [ ] **Шаг 3.** Исправить найденные ошибки, повторить только затронутые проверки, записать результат.
- [ ] **Шаг 4.** Сканер дизайна, `vibesec`, `code-review`.
- [ ] **Шаг 5.** В отчёте отдельно: работающие функции, ограничения демо, что нужно для реальных клиентов. Честно указать, что проверено только заглушкой.
- [ ] **Шаг 6.** Итог заказчику: команды запуска, переменные без секретов, инструкция по размещению, сценарий демонстрации.
